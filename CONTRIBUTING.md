# Contributing to filesonar

Thanks for taking the time. Bug reports, ideas, documentation fixes and code are all
welcome.

## Getting set up

```bash
git clone https://github.com/yacbln/filesonar && cd filesonar
python -m venv .venv && . .venv/bin/activate
pip install -e ".[dev]"
sudo apt install tesseract-ocr    # some tests need it; they are skipped otherwise
```

## Running the tests

```bash
pytest                 # fast suite: fake models, real files, real SQLite
pytest -m ollama       # end-to-end: real Ollama models and a real MCP stdio session
pytest --cov=filesonar --cov-report=term-missing
```

The fast suite needs no network and no models. Sample PDFs, Word files and images are
generated by `tests/samples.py` at test time, so the repository holds no binary fixtures.

## Changing how results are ranked

Unit tests cannot tell whether search got better. Measure it on a real index first:

```bash
python scripts/eval_search.py --mode rare        # distinctive words from each file
python scripts/eval_search.py --mode random      # ordinary words
python scripts/eval_search.py --mode paraphrase  # the local model's own wording
```

Run each with two or three `--seed` values before and after your change and include
the numbers in the pull request. The script only reads the index.

## Before opening a pull request

- `ruff check . && ruff format --check .` passes
- new behaviour has tests, bug fixes have a test that failed before the fix
- user-visible changes are described in `CHANGELOG.md` under "Unreleased"
- the README is updated if options, commands or tools changed

## Ground rules for changes

filesonar handles private files, so a few things are not negotiable:

- no new network destinations, telemetry or "phone home" of any kind (the only ones are
  the configured Ollama server and, when the user enables it, Google's Drive API)
- the built-in exclusion list (`ALWAYS_EXCLUDED` in `config.py`) can grow but never shrink
- MCP tools never modify or delete the user's files; a tool that writes anything at all
  (like `prepare_file`, which only writes to its outbox) is discussed in an issue first
- anything parsed from a file is untrusted input: bound it, and never execute it

## Adding a file format

1. Add the extension and an `extract_<format>` function in `src/filesonar/extract.py`
   returning an `Extraction`.
2. Generate a sample in `tests/samples.py` and add tests in `tests/test_extract.py`,
   including a corrupt file.
3. Mention it in the README table.

## Releasing (maintainers)

1. Move the "Unreleased" entries in `CHANGELOG.md` under a new version heading and set
   the same `version` in `pyproject.toml`.
2. Commit, then tag and push: `git tag v0.2.0 && git push origin v0.2.0`.
3. The `Release` workflow tests, builds and publishes to PyPI through trusted publishing
   (no API token exists to leak). It refuses a tag that does not match the version.
